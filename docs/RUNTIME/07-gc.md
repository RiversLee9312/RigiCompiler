# 三级 GC 与 macroGC fence（§22–§24、§28）

> 本文件是 [RUNTIME.md](../RUNTIME.md)（Rigi 运行时设计）的章节拆分，§ 编号与原文件一致；总目录与章节索引见该索引文档。

## 22. 三级 GC：microGC、microSGC 与 macroGC

Rigi 的“GC”由两层确定性 ARC 和一层候选式循环回收组成。正常路径优先由 ARC 即时解决；循环回收只处理 ARC 无法独立释放的循环候选，并按会计模式分账（§22.3）：shared 候选由 macroGC 停世界收集，local 候选由属主协程协作收集（§22.4）。

### 22.1 microGC

microGC 管理 local 对象域的 ARC：

- 管理 local Object 的强引用计数；
- 管理普通 rich ValueType/Box 内部指向 local 或 shared Object 的引用 acquire/release，其中指向 shared Object 的计数操作转入 microSGC；
- 同一 Coroutine 任意时刻最多由一个 Worker 执行，Coroutine 换 Worker 不改变其对象域。

**会计模式分流（split-heap）**：每个实例的对象头 `packedFlags` 携带 1 bit 会计模式位，标记本实例走 local 还是 shared 会计，release/acquire 路径按位分流（一个可预测分支）。shared 类型实例恒 shared 会计（数组保守同此，§22.2）；local 类型实例默认 local 会计。

local 会计的引用计数是**非原子**的普通读改写——安全性由「local 实例的计数只被属主协程触碰」保证，该不变量有三道封口：语言静态划分 local/shared（SYNTAX §3.1.1 闭包表 + 逃逸闸门）使 local 对象不能跨协程共享；跨协程引用的唯一合法形态是 Handle 壳（§28，local 目标的计数只被属主触碰，load 走借用纪律）；失败 Task 的异常图在**失败发布点**一次性整图提升为 shared 会计（promotion，§22.3）——此后按 shared 规则走，多 waiter 并发持有因此始终落在原子会计上。shell 属主终止时，仍被壳引用的子图同样原地提升为 shared 会计（§28.5）。

计数同步只保护对象生命周期，不改变语言的 local/shared 限制或对象身份，也不为普通字段读写提供同步（§3）。

当 local Object 的引用计数降为 0 时，microGC 先执行 §25 的 `IDisposable` 合约检查，再释放对象并沿 `refMap` release 它持有的引用。绝大多数短命局部小对象在这一层直接消失，不进入任何循环候选集。

### 22.2 microSGC

microSGC（S = synchronized）是 shared 对象域的同步 ARC：

- 管理 shared Object 的原子强引用计数；
- 管理 shared rich ValueType/Box 内部的 shared Object 引用；
- 支持多个 Coroutine 并发 acquire/release 同一个 shared Object。

计数降为 0 时，运行时先执行 §25 的 `IDisposable` 合约检查，再确定性释放对象。microSGC 只同步生命周期元数据，不为对象的普通用户字段提供互斥或原子语义。

当前 native 数组/连续缓冲区使用统一布局标记，生命周期保守采用原子引用计数（恒 shared 会计），包括元素类型未共享的数组。该实现选择不改变 `Array<T>` 按元素推导的共享安全规则，也不为数组元素读写提供同步。

### 22.3 macroGC 与属主协作收集

循环候选按会计模式分账两本，分别由两套收集路径处理：

- **全局候选账本（shared 会计）**：由 macroGC 经 §23 的 ownership fence 停世界后收集（§23.2）；
- **per-协程 local 账本（local 会计）**：由**属主协程自己**在安全点执行协作式收集——收集者即唯一 mutator，图天然稳定，零 fence 零锁（§22.4）。协程销毁时收干其 local 账本（终态兜底）。无协程上下文（main 流等）的 local 候选与 `$mw.*` 合成类（协程帧等跨协程机制对象）落全局兜底 local 账本（锁保护），由债务触发就地收集与 shutdown 终轮收干。

候选债务统一使用 64 位字节计数（Windows 的 `long` 只有 32 位，不能用作债务类型）。摘除单个候选只扣一次；整轮收集在 mutator fence 和账本锁仍持有、不能新增候选时清空账本并将债务归零。shutdown 完成后禁止重新登记候选，避免退出顺序错误使账本复活。

macroGC 是基于图染色的循环引用检测器。它不扫描整个堆，只处理“被 ARC release 路径波及、但未被 ARC 清理”的候选对象及其相关闭包。典型候选是 release 后引用计数仍大于 0、因而可能被循环内部引用维持的对象。候选账本对每个在册对象持有 +1 强引用：PURPLE 在册 ⟹ 对象引用计数 = 外部引用数 + 1。登记采用 pin-before-sub 协议——release 先以一次原子加法在计数上驻留一个引用（pin），再释放用户引用并尝试登记；登记成功则 pin 无偿转为账本引用，未登记则归还。pin 在登记全程驻留计数，因此账本登记窗口内对象必然存活；非在册对象的终态释放（计数归零）与账本零交互，析构免锁。在册对象的最后一次用户引用释放由 release 实现进账本锁摘除候选、归还账本引用后立即析构——确定性释放语义（§22.2）不变。收集开始时（冻结生效后）逐候选归还该 +1，使染色期计数等于真实外部引用数。local 账本的登记与 +1 语义同构但全部非原子（属主单线程无需 pin 驻留，§22.4）。

**失败发布点 promotion**：失败 Task 的属主协程正在死亡，异常图却可被多个 waiter 跨线程持有。失败发布点对以异常对象为根的整张可达图逐实例翻会计模式位（local→shared 单调，显式遍历栈防深递归），翻图完成先于任何 waiter 取得异常引用——此后该图按 shared 规则走（§22.1 的三道封口之一）。

运行时按对象体积累计候选债务；同一对象在一轮候选账本中只计一次。门槛被**有意设置得偏低**，使运行模式倾向于频繁、短小的“小步快跑”而非长时间积攒后进行大规模回收。

触发检测内嵌在 `release` 实现内：候选登记与债务累计之后比较门槛，跨越时经原子 pending 标志去重，随后通过 `GCWakeAlarm`（§23.4）通知收集执行体。收集由 **GC 协程**执行——运行时内部协程实体，绑定独占的内置 GC Executor（§23.2）。债务账本与 pending 标志是运行时内部原子状态，其更新与通知不构成托管引用图变更。

这一策略与前两层 ARC 配合：

- 能由 microGC/microSGC 直接归零的对象立即释放，尤其是大量本地小对象；
- macroGC 的候选数量和闭包通常保持较小；
- 每次图染色只触及候选相关对象，暂停窗口短，回收延迟低；
- 回收完成后从候选债务中扣除已处理对象，并继续以低门槛积累下一小批。

macroGC 的全局 pass 只处理 shared 会计候选——语言静态划分保证 shared 对象不引用 local 对象（SYNTAX §3.1.1 闭包表），macroGC 的候选闭包因此永远碰不到 local 实例。进入一次 macroGC pass 时，§23 的 ownership fence 冻结所有托管引用 acquire/release，从而得到稳定图。它冻结的是引用所有权变化，不是全部程序执行。

### 22.4 属主协作收集（local 会计）

local 账本的收集者是属主协程自己：收集者即唯一 mutator，图天然稳定，**零 fence、零锁、计数操作全部非原子**。收集算法与 macroGC 的三阶段染色同构（markGray/scan/collectWhite + 存活子引用补偿 + 两段式清理），两点系统性差异：rc 访问全部 plain（local 闭包属主独占）；候选闭包内的 shared 会计子对象整条跳过染色——shared 入边由 macroSGC/macroGC 的全局路径负责，局部候选的判死只由 local 入边决定。

触发点（安全点族）：

- **债务阈值**：local 账本按体积累计债务，跨越门槛（与全局共用 `RIGI_RT_GC_THRESHOLD` 口径）时在登记/分配路径就地收集——不挂起的密集循环由此兜底；
- **挂出点顺手小回收**：协程 yield/挂起时若 local 债务非零即顺带收集一轮，不可达环不跨挂起期滞留；
- **终止收干**：协程销毁时对其 local 账本做最终收集并释放账本——memtrack 零泄漏口径的协程侧兜底。

local 收集全程不触碰 §23 的 fence：属主是唯一 mutator，无需停世界。纯 local 工作负载因此可以全程不发生任何一次全局 fence 握手。

## 23. macroGC 轻量级 ownership fence

### 23.1 flag 布局与状态

运行时维护一组按 cache-line 尺寸独占并显式对齐的原子 flag，避免 false sharing：

- 每个 Coroutine 一个 `cFlag`：`IDLE(0)`、`ENTERING(1)`、`PROCESSING(2)`；
- GC 一个 `gcFlag`：`IDLE(0)`、`STARTING(1)`、`PROCESSING(2)`。

`cFlag.PROCESSING` 表示该 Coroutine 正处于一个引用 acquire/release 区域；`ENTERING` 表示它试图进入但因 macroGC 已开始而在 `GCAlarm` 上等待。

`cFlag` 的协议身份必须绑定 Coroutine，而不是 Worker：Coroutine 是 Rigi 最小且稳定的串行执行/所有权主体，同一 Coroutine 任意时刻最多由一个 Worker 执行；Worker 只是 Executor 内透明且可替换的执行载体。Coroutine 在 `GCAlarm` 上挂起后释放原 Worker，恢复时可以由同一 Executor 的任意 Worker 继续，因此 `ENTERING → Suspended → 恢复 → retry` 的状态必须随 Coroutine 保存。实现不得让 macroGC correctness 依赖挂起前后的 Worker 绑定、Worker 生命周期或具体调度队列结构。Worker-local 缓存可以作为不可观察优化，但不能取代 Coroutine-owned `cFlag`。

### 23.2 GC 侧协议

执行 macroGC 的 collector 是 **GC 协程**：运行时初始化时创建、进程常驻的运行时内部协程实体，永久绑定运行时内置 GC Executor——§20 内置 Executor 之外的实现级 Executor，自带 Worker，不向 stdlib 公共面暴露，用户协程不可进入。GC 协程在两轮收集之间挂起于 `GCWakeAlarm`（§23.4）；被唤醒后执行下述握手与收集。**从发布 `STARTING` 到发布 `IDLE` 之间，GC 协程不得挂起**（否则全体有 acquire/release 需求的 Coroutine 将堵在 `GCAlarm` 上，直至它被重新调度）。一轮收集结束（发布 `IDLE` 并触发 `GCAlarm`）后，GC 协程清 pending 标志并复查候选债务：仍超门槛则立即开始下一轮，否则重新挂起于 `GCWakeAlarm`。

macroGC 开始时：

1. 原子地将 `gcFlag` 从 `IDLE` 更新为 `STARTING`；只有成功完成该状态转换的 collector 可以启动本轮 macroGC。
2. 在该原子操作后建立 fence，禁止后续对 `cFlag` 的巡视和清理指令被重排到发布 `STARTING` 之前。
3. 自旋巡视全部已注册 `cFlag`，直到每个 flag 都不等于 `PROCESSING`。引用修改区是编译器生成的短代码，且不含挂起点与可抛出点（§23.3 不变量），这一排空阶段有界且预期很短；`ENTERING` 和 `IDLE` 都不阻止 GC 继续。
4. 原子地把 `gcFlag` 置为 `PROCESSING`，开始候选闭包的图染色与清理。此时托管引用图和 ARC 计数对普通 Coroutine 保持稳定。
5. 对确认不可达的对象执行 §25 的 `IDisposable` 合约检查并完成清理；在发布结束前建立 fence，禁止清理和元数据写入被重排到结束状态之后；随后原子地把 `gcFlag` 置为 `IDLE`。
6. 触发本轮内部 `core.GCAlarm`，唤醒所有处于 `ENTERING` 的 Coroutine。

### 23.3 Coroutine 侧 acquire/release 协议

编译器在所有托管引用 acquire/release 操作外生成进入协议。概念流程如下：

```text
retry:
    fence
    if gcFlag != IDLE:
        cFlag = ENTERING
        yield core.GCAlarm(currentGeneration)
        goto retry

    cFlag = PROCESSING
    fence              // 保证 PROCESSING 在第二次 gcFlag 检查前对 GC 可见

    if gcFlag != IDLE:
        cFlag = ENTERING
        yield core.GCAlarm(currentGeneration)
        goto retry

    perform acquire/release region

    fence              // 保证区域内引用图和 RC 写入先完成
    cFlag = IDLE
```

双重检查关闭了 Coroutine 与 GC 同时进入的竞态：如果 Coroutine 先进入 `PROCESSING`，GC 必须等待它退出；如果 GC 先发布 `STARTING`，Coroutine 会在第二次检查时退到 `ENTERING` 并挂起。

一个复合引用操作可合并为同一 acquire/release region，例如 rich ValueType 整体复制可在一次进入中 acquire 新内部引用、替换存储并 release 旧内部引用。递归 release 继续复用当前 region；实现可用 Coroutine 本地嵌套计数，只有最外层进入/退出实际修改 `cFlag`。

托管局部槽释放旧值时，必须在同一 region 内将槽清零并撤销其所有权。后续产出指令可能抛异常；此时异常清理只能看到空槽，不能重复释放已经归还的旧值。对象胖引用、String 和 rich ValueType 均遵守此规则。

region 必须满足两条不变量：

- 内部不得含挂起点；
- 内部不得含可抛出 Rigi 异常的调用（运行时调用自身不抛异常）。

前者保证 §23.2 第 3 步的排空有界；后者保证异常 unwind 不穿越 region——acquire/release 的 fence 配对在任何控制流路径上都完整。

两条不变量对运行时内部代码与用户代码同等适用：调度 loop（§17.4 的 Dispatcher 循环与 Worker 取任务路径）自身产生的托管引用操作只在不跨挂起点的 region 内完成，调度 loop 不在挂起等待期间保持 region 开启。

### 23.4 GC Alarm 族：`core.GCAlarm` 与 `core.GCWakeAlarm`

源码中看不到 GC 等待语句。`yield` 在此处特指编译器生成的隐藏语句：

```rigi
yield core.GCAlarm(...)
```

`GCAlarm` 是运行时内部的 `core.coroutine.EventAlarm`，服务于在 ownership fence 上等待的 Coroutine。等待者进入 `Suspended`，不会以裸 `yield` 反复进入 Runnable 集合。它使用 EventAlarm 的原子 waiter 注册/触发握手，保证 GC 在注册前后完成都不会丢失唤醒；恢复后 Coroutine 必须重新执行完整双重检查。实现可以用 GC generation 区分连续的 macroGC pass。

`GCWakeAlarm` 是第二个运行时内部的 `core.coroutine.EventAlarm`，方向相反：它由 `release` 路径上的门槛跨越（§22.3）触发，用于唤醒挂起其上的 GC 协程。触发幂等且保持已触发状态直到被消费（sticky，§19.3），waiter 恒为 GC 协程（至多一个）；唤醒延迟有界——GC Executor 的 Worker 不与用户协程共享。`GCWakeAlarm` 的触发是经原子 pending 标志去重后的运行时内部原子操作，不构成托管引用图变更（§23.5）。

两个 Alarm 均为运行时内部实体：不属于 §26 的原生方法面，不进 stdlib，也没有任何跨层可见形态。

### 23.5 fence 覆盖的操作

“修改引用图”被定义为所有托管引用的 acquire 和 release，包括：

- 在栈、Coroutine frame、对象字段、容器槽或 rich ValueType 字段中建立一个强引用；
- 覆盖、清空、移出或销毁上述引用槽；
- rich ValueType/Box 复制时 acquire 内部引用，覆盖或销毁时 release 内部引用；
- ARC 归零后的级联字段 release；
- 修改与循环候选账本、引用计数和图边一致性直接相关的运行时元数据。

引用槽写入、对应 RC 更新和候选元数据更新必须作为同一个 acquire/release region 对 macroGC 保持一致。候选账本持有的 +1 强引用（§22.3）属于运行时内部所有权：登记在 release region 内完成（pin 先于减量驻留），收集开始时的归还发生在冻结生效之后，两者都不改变外部引用数的语义。

会计模式分流后，fence 的语义约束对象是 **shared 会计**操作——macroGC 的全局 pass 只遍历 shared 闭包，需要冻结的也只是这条会计线。local 会计操作不依赖 fence（属主协作收集以「属主即唯一 mutator」替代停世界）；实现上 region 进出仍统一发射（形态保守、经快路径后开销极低），不改变上述语义划分。

### 23.6 特别放行：分配与纯值执行

macroGC 不阻止单纯的内存分配或不涉及托管引用的执行：

- Object、Box、Span buffer 的原始内存分配可以在 `STARTING`/`PROCESSING` 期间继续；
- 对象头和纯数值字段初始化可以继续；
- 非 rich ValueType 的创建、复制、传参、返回、栈上运算完全不经过 GC fence；
- 尚未向任何托管引用槽发布的新对象可以继续完成纯值初始化。

只有当代码尝试给新对象添加托管引用、把新对象放入栈/Coroutine frame/字段等正式引用槽，或操作 rich ValueType 的内部引用时，才会撞上 acquire/release wall 并在必要时等待 `GCAlarm`。因此 macroGC 的“停顿”严格局限于 ownership mutation；大量数值代码、原生 buffer 工作和未装箱的非 rich ValueType 计算可以无感继续运行。

## 24. macroGC 的性能取向与可观察语义

macroGC 的低触发门槛、候选闭包扫描和 ownership-only fence 共同形成以下性能模式：

1. ARC 先清除绝大多数无环对象，特别是 Coroutine 本地的小对象；
2. 少量未清除对象很快达到按字节计的低门槛；
3. macroGC 频繁启动，但每次只处理很小的候选闭包；
4. `STARTING` 只等待已有的短 acquire/release region 排空；
5. `PROCESSING` 期间只有新的 acquire/release 被 EventAlarm 挂起，纯值代码和分配继续；
6. GC 完成后集中唤醒等待者，它们重新检查后继续原操作。

会计模式分流（§22.1）把上述停世界协议约束在 shared 会计线上：local 对象的 ARC 与协作收集（§22.4）不进 fence、不取账本锁、计数非原子；纯 local 工作负载可以全程不发生任何一次全局 fence 握手。Handle 壳（§28）与失败发布点 promotion（§22.3）把仅有的两类跨协程引用形态也封在原子会计内，是分流安全的前提。

语言不承诺具体阈值数值、图染色颜色编码或候选容器结构；这些属于运行时调优参数。但实现必须保持“按候选体积触发、默认门槛偏低、只处理候选相关闭包、非 ownership 工作继续执行”这四项语义与性能取向。

## 28. Handle 壳：capability 计数与目标生命周期

`Handle\<T>` / `MutableHandle\<T>`（SYNTAX §3.1.2）的目标生命周期由运行时内部的**壳**（capability shell）管理。壳把「Handle 的共享计数」与「目标的锚定保活」解耦：Handle 的复制与释放只在壳计数上做原子运算，目标引用始终由壳持有，最后一枚 capability 消失时目标经属主通道确定性释放。本节描述壳的布局、注册表、增减量协议、属主挂起栈消化与 macroGC 配合；语言面语义（expose、load、asMutable、store）不受影响。VM 宿主以 hook 模拟同一协议，双宿主行为对拍一致。

### 28.1 计数壳与 capability 布局

壳是运行时内部对象，以 `shellID` 为身份（进程内全局唯一、永不复用，0 为无效保留），持有三类状态：

- **target 锚引用**：一枚 target 胖引用，壳创建时恰好一次 acquire——这是整个 capability 生命周期内唯一一次目标 acquire；
- **原子 count**：存活 capability 对象数（原子 i64）；
- **owner_reg**：属主注册表指针（指向属主分组表或全局索引表）。

capability 对象（`.handle`，48B 固定 ABI）由 16B 对象头 + 壳指针 + shellID + 可写能力位（mutable）+ kind 组成，**refMap 恒为 0**：capability 不持任何受管引用，目标存活完全由壳锚保证。`count ≥ 1 ⟹ 壳必活`，目标解析与计数增量因此经壳指针直达、无注册表查找；shellID 仅作为属主挂起栈载荷与注册表查找键。

Rigi 侧 `Handle\<T>` / `MutableHandle\<T>` 仍只持 capability 字段（§3.1.2 的固定布局对象存储），语法与身份规则零变化。复制 Handle 是 capability 的普通 shared ARC 拷贝；`asMutable()` 经源 capability 的壳指针 increment 派生新 capability——直接原子加，不新建壳、不二次锚定。

### 28.2 注册表：全局索引与属主分组

壳的注册形态是两张表：

- **全局索引表**（shellID → 壳）：壳的唯一真存储，兜底所有查找；
- **per-协程属主分组表**：挂 RigiCoHandle，供属主终止时整组遍历过户。

两张表统一由一把全局自旋锁保护；属主挂起栈的压栈（发布者）与弹栈（属主槽消化）双方在查表/摘表时都经此锁串行，属主表不是属主独占。锁内读分组表指针一律经壳的 owner_reg，与 teardown 的整组改指、注册表本体释放串行。

### 28.3 增量与减量：归零转移

- **增量**：直接对壳 count 原子加（§28.1，不新建壳、不二次锚定）。
- **减量**（capability 析构，挂 ARC 析构钩子）：经壳指针 `fetch_sub`。old > 1 直接完成，无任何投递；old == 1（**归零转移**）才委托释放——目标的最终释放不在减量线程就地执行，而是转交属主通道（§28.4）；壳已过户到全局表时（§28.5）由任意线程就地清理。

### 28.4 属主挂起栈与属主槽消化

归零转移发生时（壳仍属 per-协程属主表），运行时把 `shellID` 压入**属主协程的挂起栈**——挂在 RigiCoHandle 槽位上的 MPSC 无锁侵入式栈：多发布者 CAS 压栈（release），属主互斥单消费者弹栈（acquire）。压栈前发布者经 `native_rc_retain` 验活 pin 住属主句柄：pin 成功 ⟹ teardown 未启动（NativeRc 归零 release 先摘注册表条目再回调析构），压栈与 teardown 互斥，pin 释放即使恰为最后强引用，teardown 也会过户并排空已压项；pin 失败 = 属主已死，投递方转兜底内核——锁内重查归属、补 promote 子图后清理（§28.5 过户完成的壳走全局直接分支）。发布者线程对壳只做 count 减量、压栈与死属主兜底，**绝不清壳**。

消化发生在**属主互斥执行槽**内（协程句柄 resume 的执行门闸内，段前与段后各一次 `rigi_shell_drain_pending`，属主终止 teardown 再终局排空）：逐枚弹栈 shellID → 查全局索引，按壳的归属分流：

- 壳已不存在（重复或迟到投递）：幂等丢弃；
- 壳仍属已终止属主：就地补 promote 子图后清理；
- 其余：摘表 → anchor release → 释放壳本体——anchor release 因此恒在属主上下文（或已过户的 shared 会计上）执行，发布者线程触碰 local 会计的模型纯度让步点随 3b-δ2 封口。

弹栈点互斥性：resume 在途必有 Dispatcher 泵的强引用持握（⟹ teardown 无法并发）；teardown 在途则 token 已死（⟹ 无 resume 在途、无新压栈可 pin 成功）。

不设发布者唤醒信号：Dispatcher 的 carriage 与协程恢复严格条件门控（裸 yield/轮询自重排；await/EventAlarm 恢复被 Task 终态/信号门控，恢复块重回 wait 块经非幂等的 waiter 登记）——以属主 token 发额外 carriage 会造成 waiter 重复登记与续体双执行。拾取延迟因此为「属主下一个执行槽或 teardown」：属主段内释放当段尾即清；跨线程释放最迟属主下一次恢复（门控唤醒自带 happens-before）或 teardown。`count == 0 ⟹ 无 capability 可再触达壳与目标`，延迟只延长锚引用寿命，语义不可观测。

清理权唯一：属主终止不清壳（除 teardown 末尾的挂起栈终局排空——彼时壳已过户，属全局分支就地清理），只做 §28.5 的过户；就地清理只发生在 §28.4 的属主槽消化与 §28.6 的冻结期拆解。

### 28.5 属主终止过户

属主协程销毁时（句柄 teardown，子图失效前）：锁内摘属主分组链，逐壳把 owner_reg 原子改指全局索引表，并对子图逐对象 promote shared 会计；壳物理不动。过户后壳的锚引用可被任意线程安全触碰，后续归零转移不再入属主挂起栈，由任意线程就地清理（§28.4 第二条分流由此消解为兜底路径）；teardown 末尾终局排空挂起栈残留归零壳（已过户 → 全局分支清理）。

### 28.6 与 macroGC 的配合：代理边与冻结期分流

capability refMap=0 切断了 GC 图上 capability→target 的边。macroGC 对 capability 特判恢复**代理边**：图染色把壳锚作为 capability 的代理图边接回三阶段协议——markGray 扣 target 的壳锚成分，scanBlack/补偿原路加回；白色批清理经 capability 壳分支的 raw_release 配对（白色同胞边整条跳过）。代理边与 capability 持隐藏 target 时代的 refMap 边在图形与计数语义上严格一致，capability 仍不持受管引用。

GC 冻结期（fence `PROCESSING`，§23）capability 归零**不入属主挂起栈**——冻结期公共 release 面与 Dispatcher 会自锁——改为就地原始拆解：锁内摘双表，target 经 raw_release 拆解后放壳，与白色批清理协议一致。

壳会计与目标的 shared 会计位分流兼容：未提升时壳的 anchor 释放走 local 会计（原子实现，行为安全）；teardown promote 后为 shared 原子。代理边的扣加只作用于壳锚成分，候选账本的 pin-before-sub 协议（§22.3）与其互不干扰：候选账本 +1 属运行时内部所有权，代理边保持「外部引用数」语义不被 capability 自身计数污染（§23.5）。

3b-δ1 起 `handle_target` 已借用化：壳指针直达解析、返回裸胖引用（**不再 acquire**）——load 解析过程不再触碰壳锚对目标的引用计数；语言级借用槽机制（native 声明 `@NativeBorrow` 标记 + RcInjection 借用槽传播：copy/cast 链传播、出口与 Emit 读侧 cast 裸取协同配平、存储逃逸编译拒绝）已落地。`handle_load` 因 Cell 值拷贝路径（kind 1/2）保持值语义，整体仍为 owned 契约——对象路径在 handle_load 内部全程借用裸取，返回边界由 `$mw.ret` acquire 提升为拥有后交调用方（行为配平）；「load() 调用方零义务」的整链借用化受出口粒度契约限制，随 3d 设计再裁定。借用寿命纪律见 `SYNTAX/02-type-system.md` §3.1.2。
