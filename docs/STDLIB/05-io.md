# 各 NS 的最小能力：core.io（§4.4）

> 本文件是 [STDLIB.md](../STDLIB.md)（Rigi 标准库 MVP 设计）的章节拆分，§ 编号与原文件一致；总目录与章节索引见该索引文档。

### 4.4 `core.io`

核心抽象是可由用户继承实现的 `InputStream` 和 `OutputStream` 抽象类，均实现 `IDisposable`。通用精确读取和流传输由基础实现组合底层读写完成。
MVP 包括内存输入/输出流、缓冲输入/输出流、`AutoBuffer`、`pipe`、精确读取、基于编码器的 `TextReader`/`TextWriter` 和控制台输入/输出/错误输出。保留已有 `Console.println` 用法和公开 API 的原子性，内部切换到流实现。

**已确定的基本读写契约：**

- 使用现有 `Span<u8>` 作为紧凑字节缓冲区。它在 Rigi 中是持有连续存储的对象，不是其他语言中的栈借用切片。
- 单次操作的 `offset`、`count` 和 `read` 返回的实际读取字节数均使用 i32；读取允许少于请求数。
- `count > 0` 时以返回 0 表示 EOF；暂时无数据应挂起等待，不用 0 表示“稍后再试”。
- `count == 0` 时校验参数后返回 0，不消费输入，也不证明已到 EOF。
- `write(buffer, offset, count)` 无返回值，成功返回即写完全部请求范围，底层短写由实现继续完成。
- 失败不保证回滚已消费或已写出的字节。
- `offset/count` 非负且在范围内，检查加法溢出；零长度不绕过范围验证。
- 累计字节数与文件/流位置使用 i64，与单次缓冲区索引分开；这不表示基础流必须提供查询位置或 seek 的能力。
- `read` / `write` 均为普通 `func`，不声明 `async`，不返回 Task。内部等待可挂起当前协程并释放 Worker，恢复后继续同一次调用；不另建协程，也不因此要求流或缓冲区为 shared。此语义沿用 [函数 §4.5](../SYNTAX/03-functions.md) 与 [协程 §17.2](../RUNTIME/06-coroutines.md)。
- 传入的缓冲区只在调用期间借用，包括挂起期间；正常返回或抛出异常后，不再通过后台操作访问该缓冲区。调用者在操作完成前不得修改或复用相关范围。缓冲输出流若延后写出，先复制到自己的缓冲区。

**已确定的精确读取契约：**

- `readExactly(buffer, offset, count)` 使用普通函数，缓冲区与范围类型同 `read`。循环调用 `read`，填满指定范围后成功返回，无返回值。
- 填满前遇 EOF，抛出 `core.io.EndOfStreamException : core.IOException`，携带本次请求字节数与实际已读取字节数，二者均为 i32；不把部分结果当作成功。
- 失败时保留已经读入缓冲区的数据，不回退流位置。其他 I/O 错误原样传播，不改报为 EOF。
- `count == 0` 时仍校验参数与流状态，通过后直接成功，不消费输入。

**已确定的定位与便利操作：**

- 定义 `ISeekableStream` 接口，只提供 `seek` 和 `getPosition`，不把长度查询塞入此接口。基础输入/输出流不强制实现它，文件流和内存流按具体能力实现；位置以字节计，使用 i64。
- 可定位流允许定位到末尾之后；定位本身不扩容，后续写入时空隙补零，仍受具体存储的容量限制。负位置或不可表示的位置报错。缓冲流与文本流首版不直接暴露定位；通用流及 ISeekableStream 不提供 `setLength`，具体可定位文件输出流按 §4.5 提供此能力。
- 提供整个 `Span<u8>` 的读写重载，以及 `readByte(): u8?`、`writeByte(...)`；`readByte` 用 null 表示 EOF。首版不提供 `Array<u8>` 读写重载。
- `readAll` 直接返回的字节结果只使用 `Span<u8>`；允许指定 `maxBytes`，超限抛错，不返回静默截断结果。未指定时受返回容器容量上限约束，不承诺任意大结果都能整体装入内存。
- 需要动态扩容的字节缓冲区时使用 `AutoBuffer`，通过 `getOutputStream()` 获得输出流，再由输入流的 `pipe` 写入；通过 `getInputStream()` 流式读取其内容，不要求先整理成单个完整 Span。
- 流传输方法命名为 `pipe`，不使用 `copyTo`。它使用有界缓冲传输到 EOF，成功返回累计 i64 字节数；不关闭任何一端，也不自动调用目标流的 `flush()`。失败保留已发生的读写，不回滚；不支持源和目标实际指向同一条流的传输。

**已确定的内存流与缓冲包装器：**

- 从已有 Span 构造的普通内存输入流默认复制输入数据，形成固定快照；普通内存输出流导出的 Span 也是独立副本。首版不暴露内部可变缓冲区，输出结果在 `dispose()` 前取出；内存流遵守关闭后的操作限制。
- `AutoBuffer` 负责动态扩容的 u8 存储，其输入/输出流是上述流式访问入口。它与普通内存流导出单个 Span 的便利入口分开；不把 AutoBuffer 作为 `readAll` 的另一种直接返回类型。
- `AutoBuffer.getInputStream()` 和 `getOutputStream()` 返回的流均实现 `ISeekableStream`，每次创建独立游标。输入流初始位于开头；输出流初始位于当时的末尾，默认从此追加，显式 `seek` 后按新位置写入，覆盖已有范围或扩展内容。
- AutoBuffer 的流直接访问其内容，不是创建时固定的内容快照。按顺序追加后，已有输入视图可继续读到新增数据；读到当前末尾即返回 EOF，不等待未来写入。关闭视图不清空 AutoBuffer，各视图及对 AutoBuffer 的访问之间也不支持并发读写。
- 缓冲容量可配置，默认 16 KiB。缓冲输入流允许预读，底层流位置可能领先于调用者已经消费的位置。
- 包装器使用期间不能绕过它操作下层流。销毁输入包装器不自动回退预读位置，未消费的缓冲数据会丢弃；关闭 reader 不继续读取或校验未读完的内容。

**已确定的所有权契约：**

- Serializer 借用调用者传入的流，不因序列化成功或失败而关闭该流。
- `TextReader`、`TextWriter` 和缓冲流包装器默认借用下层流。创建/打开下层资源的一方明确负责关闭，不能依赖包装器替自己关闭资源。
- 借用不免除包装器自身的清理责任；包装器的 `dispose()` 清理自身状态，但不关闭借用的下层流。通过构造参数传入 `StreamWrapperOwnership` 枚举，成员为 `.Borrowed` 和 `.Owned`，默认 `.Borrowed`；只有显式 `.Owned` 才接管下层流的关闭责任。
- 只有构造成功才接管关闭责任；包装器构造失败时，下层流仍由调用者负责关闭，构造过程自行清理已建立的内部资源。
- 资源创建者通过 `IDisposable` 和 `seq using` 管理各层生命周期。先绑定下层流、再绑定包装器，按既有规则逆序清理，使包装器先收尾、下层流后关闭；借用的下层流在包装器使用和收尾期间必须保持可用。沿用 [seq 块 §6.2](../SYNTAX/05-seq-block.md) 的规则，不引入隐式所有权转移。

**已确定的关闭与刷新契约：**

- `flush()` 的成功返回表示此前写入已经真正完成。它提交本层待输出的缓冲，逐层调用下层输出流的 `flush()` 并等待全部完成；不能仅把任务排入后台队列后返回。成功后仍可继续写入，不结束编码器，也不关闭流。
- 文件流的 `flush()` 必须完成操作系统提供的持久化刷新后才返回；仅完成写入系统缓存不满足此契约，持久化刷新失败必须报告错误。内存目标完成内容写入；非文件设备按其支持的输出语义等待写出完成，不能把文件持久化调用机械套用到所有句柄。文件实现与平台依据见 §4.5。
- 正常状态的输出流在 `dispose()` 中完成剩余写出和刷新；输出包装器还须结束编码并刷新下层流，随后清理自身。借用模式不关闭下层流，显式拥有模式承担下层流的关闭责任；故障状态的收尾遵循下述规则。
- `dispose()` 幂等：首次调用完成后，即使收尾、刷新或资源释放抛出异常，对象仍进入关闭状态。后续 `dispose()` 无操作，不重试编码、写出、刷新或释放。
- 首次 `dispose()` 的写出或刷新失败不得跳过其余必要清理，仍须尝试清理自身及关闭拥有的下层资源，并向调用者报告失败。关闭状态不表示失败的写出或底层释放已经成功；失败不回滚已经写出的数据。
- 关闭后读、写或 `flush()` 抛出状态异常；回调不能访问已释放的句柄或缓冲区。`dispose()` 挂起期间继续遵守既有资源保活和清理展开规则。

**已确定的错误与调用边界：**

- 流区分正常、故障和关闭状态。参数校验失败、普通 EOF 以及 `readExactly` 的提前 EOF 不使流进入故障状态；实际 I/O 或编解码失败后进入故障状态，只允许清理，不继续读写、定位或刷新。
- 故障输出流的 `dispose()` 不重写可能已经部分提交的数据，但仍清理自身并释放拥有的下层资源。下层流的清理遵循其自身状态；失败不等于免除清理责任，也不把借用变成拥有。
- 范围错误使用 `core.OutOfBoundException`，关闭或故障状态使用 `core.IllegalStateException`。系统 I/O 错误保留操作名称及可用的原生错误码；精确读取提前 EOF 使用前述 `EndOfStreamException`。
- 异常直接遵循现有 `try/catch/finally` 模型，每次只向外传播一个异常，不增加聚合异常类、异常集合或另行规定的优先级。清理期间 `finally` 抛出新异常时，按既有展开规则替换原先正在传播的异常；其余必要清理仍通过现有清理路径执行，不因保留错误而跳过资源释放。
- 普通流与包装器使用 local 类型。同一流实例不支持并发或重入操作，这是实现者必须遵循的设计契约；调用挂起期间仍属于同一次操作。首版不提供同步包装器，控制台公开 API 的原子性由外层协调实现。
- 首版不加入流专用取消令牌或超时参数，不把并发调用 `dispose()` 当作取消。等待与资源保活继续使用既有协程机制。

**已确定的文本流契约：**

- 文本适配器接收编码器，首版内置 UTF-8。默认严格拒绝非法编码，替换模式显式选择；读取默认识别并跳过流开头的 UTF-8 BOM，写入默认不生成 BOM，不自动猜测其他编码。
- `TextReader` 提供 `readChar`、`readLine`、`readToEnd`。`readChar` 返回 §4.3.1 定义的 `char?`，一次读取一个完整 Unicode 标量，EOF 返回 null；`readLine` 返回不含换行符的 String，空行返回空串，没有任何剩余内容时才返回 null，末尾没有换行的最后一行正常返回。
- `readLine` 识别 LF、CRLF 和单独 CR；`writeLine` 默认输出 LF，允许显式配置 CRLF。普通 `TextWriter` 不因写了一行就自动刷新。
- `readToEnd(maxBytes: i64)` 和 `readLine(maxBytes: i64)` 的上限均按结果 String 的 UTF-8 字节数计，而不是 Unicode 标量数；负上限抛 `core.OutOfBoundException` 且不消费输入。超限同样抛该范围异常，不静默截断、不把读取器置为故障态；结果恰等上限可正常返回，零上限仍允许空行，EOF 无剩余内容仍返回 null。单行结果不含的 LF、CRLF、单独 CR 以及流首跳过的 BOM 均不计入上限。`readLine` 实现逐标量求 UTF-8 宽度（1–4 字节），在追加到结果前先用剩余容量检查，避免 i64 累计加法溢出。
- 整体文本读取与写入是 TextReader/TextWriter 面向任意 InputStream/OutputStream 的通用能力：TextReader.readToEnd 读取剩余文本，TextWriter.write 接收完整 String 并按配置编码写出；调用方式为普通函数，不要求底层是文件。整体字节读取与写入沿用 InputStream.readAll、OutputStream.write 的 Span 重载，不把原始字节操作塞进文本适配器。
- 这些便利能力不接受 Path，不负责打开、创建、截断或选择追加文件；追加位置和覆盖行为由已有流及其打开模式决定。core.fs 不重复提供 File.readAllText/readAllBytes/writeAllText/writeAllBytes/appendAllText/appendAllBytes 等路径便利入口。
- 整体读取/写入同样遵守默认 Borrowed，不因一次操作结束而自动关闭传入流，也不因写入一个完整 String 或 Span 而自动 flush。需要完成输出时由调用者显式 flush，或通过已定的正常 dispose 收尾；包装器与底层流分别按既有所有权和 using 规则管理。便利层不改变错误传播、部分结果副作用或输入预读规则。

**已确定的标准流与控制台契约：**

- 标准输入、输出、错误输出通过可独立关闭的借用包装对象提供。关闭对象只结束该对象的使用，不关闭进程标准句柄，也不影响其他包装对象。
- 标准输入的多个包装对象共享同一输入位置，不能当作独立输入源使用。标准输入读取原始字节，包括 CR、LF、0x1A；不得由宿主文本模式折叠 CRLF 或将 0x1A 当作 EOF。
- 标准输出与标准错误输出是相互独立的字节流；写出的字节须与请求范围逐字节相同，包括 LF 不得由宿主文本模式扩展为 CRLF；一次 `write` 可以结束在 UTF-8 多字节序列内部，下一次同通道 `write` 可以续写，不要求每次写入自身构成可解码的文本。与 `Console.println` 等文本调用混用时，同通道按实际调用顺序排列字节；文本调用以 UTF-8 字节写入，不能在 `write` 边界提前解码或将不同通道的字节拼接解码。显示/测试需要文本时才对同通道完整输出作一次 UTF-8 解码；非法完整流沿用宿主输出的替换字符策略，不改变 `TextReader`/`TextWriter` 的严格编码策略。
- 保留 `Console.println` 等既有外部 API 的原子性，内部改用流实现。对于同一进程经标准库写入同一路标准流的操作，一次行输出不会被其他调用插入，并在调用结束前完成刷新；stdout 与 stderr 分别保证，不承诺二者的统一顺序。
- 标准输出重定向到文件时遵守文件流的持久化 `flush()` 契约；终端或管道按实际设备能力完成写出。外层协调原子性不能放宽普通流实例不支持并发的契约。

流式操作可以使用有界缓冲，但 `readAll`/`readToEnd` 仍需要完整结果内存。
不能把“流 API”描述成所有上层操作都具有常量内存。
