## 3. 跨模块原则

### 3.1 普通调用可以挂起

Rigi 从 `main` 开始就在协程内执行。普通函数、方法及普通 lambda 可以通过 `await`/`yield` 挂起当前协程；`async` 的含义是调用时另建协程。

新增流、文件、文本和序列化 API 默认使用普通函数。流的 `read` / `write` 使用普通 `func`，不声明 `async`；调用者直接取得读取数量或等待写入完成：

- 不因内部等待 I/O 而要求 `readAsync`/`writeAsync` 双套 API。
- 不为一次普通读写自动创建额外 Task；需要并发时由调用者使用现有协程能力。
- 等待期间释放 Worker，恢复时允许换 Worker，不构成跨协程传值。
- local 流、解码器、Serializer 和工作集合可以跨本协程的挂起点存活，无需因此标记 `shared`。
- 此原则不改变现有已声明为 async 的消息或原子集合 API。

### 3.2 数据与资源生命周期

- 外部资源经 `IDisposable` 和 `seq using` 管理，GC 不代替用户调用 `dispose()`。
- `dispose()` 也是普通可挂起函数，遵循现有清理展开规则。
- 接收已有资源默认借用，传参不隐含所有权转移；创建/打开资源的一方负责通过 `IDisposable` 和 `seq using` 管理关闭。包装器只有在显式选择拥有下层资源时才承担下层资源的关闭责任。
- `shared` 只证明可以跨协程共享，不提供并发读写、游标或缓冲区的互斥保证。
- 挂起中的读写、关闭和 native 回调必须有明确的资源保活与收尾策略。

### 3.3 Rigi 与 native 的边界

集合算法、缓冲管理、文本处理、格式解析、序列化流程和配置逻辑优先使用 Rigi。
系统调用、原生文件资源、时钟及访问内建字符串表示所必需的原语才进入底层。

新增 native 原语同时定义 VM hook 与 native 行为，并复用现有资源句柄和事件底座。
文件操作可以由宿主事件或工作线程完成；不能把阻塞系统调用直接放在 Compute Worker 上，再把整个函数标成 async 当作非阻塞实现。文件打开也不例外：Linux FIFO 无对端时 `open` 可无限等待，普通文件流必须以非阻塞方式完成受控打开、按已打开句柄确认普通文件（目录与其余非普通文件分别报 IsDirectory/WrongType），而非事先 stat 路径或在 Compute Worker 同步等另一端。

`Serializer` 的对象包装层使用 Rigi，复用 `Serializable` 的对象编解码入口；JSON 按目标类型读取时通过通用反射 API 查询字段类型，再构造符合目标声明的 SB 表示。不为 JSON 增加专用的编译器对象遍历逻辑或特殊语法。公共字段反射、SB 动态访问及严格的 `fromParcel` 检查属于实现前置，不能假定现有 API 已经具备这些能力。

### 3.4 基础行为一致性

- 参数、边界、缺失值、EOF、格式错误与系统 I/O 错误须可区分。
- 不因补库更改既有索引越界读 null、写越界抛异常等规则。
- 长度与偏移宽度依据具体容器明确声明，不顺便统一既有 ABI。
- 文本行为与 JSON 数值解析不依赖操作系统、系统语言或宿主地区设置；Unicode 数据与算法范围按 §4.3 固定。
- 高级便利函数组合已有底层 API，并说明是否整体读入内存。
