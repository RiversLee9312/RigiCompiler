# 各 NS 的最小能力：core.serialization.json（§4.7）

> 本文件是 [STDLIB.md](../STDLIB.md)（Rigi 标准库 MVP 设计）的章节拆分，§ 编号与原文件一致；总目录与章节索引见该索引文档。

### 4.7 `core.serialization.json`

提供 `JsonSerializer : Serializer`、JSON 专用选项和解析异常。词法/语法解析与 SB 转换使用 Rigi，不用宿主 JSON 对象序列化器代替公共模型。

JSON 语法参考 [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259)。MVP 支持对象、数组、字符串、数字、布尔、null 及完整单值根节点。以下公共行为与值映射均已确定。

#### 4.7.1 读取入口与目标类型

除基类入口外，JsonSerializer 提供普通泛型方法：

```rigi
pub func readAs\<T with Serializable>(input: InputStream): T
```

`readAs` 使用 T 的类型元信息，也应支持调用者已有的 `Type\<T>` 值作为目标类型信息；后者所指的实际类型必须在 T 的边界内并具备 Serializable。重载的参数拼写随通用反射 API 一起落实，不把动态类型值伪装成静态泛型实参。

- `read(input)` 用于读取 SB 表示，不实例化业务对象。有 Rigi 对象类型标识时保留为相应的 Parcel；已登记的类型可提供字段解析信息，未知但结构合法的类型标识仍可保存在表示中，到请求恢复对象时才报未知类型。
- 无目标类型、也无类型标识的 JSON 对象读为 `Map\<String, Any?>`，数组读为 `Array\<Any?>`。空对象和空数组保持不同；null 是实际 null。未知对象的字段只能按无目标规则读取，不能宣称已恢复其精确字段类型。
- `readAs` 支持没有 Rigi 元数据的普通 JSON。目标声明为自定义对象时，按反射取得的字段及类型构造对应 Parcel；声明为 Map 时，按字典读取；递归到每个成员时重复这一判断。不能仅凭 JSON 的 `{}` 形状或成员名字猜测对象与字典。
- 在普通 JSON 的目标 Map 上，`.rigi.type-identifier`、`content` 等成员名都是业务键，不能被自动剥离。即使前者的值是普通 String（如 `"ordinary"`），只要不是完整的 Map 规范类型名，String 键目标仍须保留它与其值；对象字段及 Array/List 中的 Map 同样如此。只有值为完整闭合的 Map 类型标识时才按 §4.7.3 包装读取，此时缺失 `content`、`content` 非数组或条目畸形必须报错，不可捕获后回退成普通字典。非 String 键目标不能把未识别为 Map 包装的 JSON 对象成员名转换为键。无目标 `read` 对明确类型标识对象的解释不受此目标类型防御规则影响。
- 字段或容器元素声明提供数值宽度、char/String、Array/List、键值类型及可空信息。空容器仍可依声明恢复；没有具体类型信息的 Any 值不能凭空恢复某个业务类型。
- 类型引导的解析直接构造匹配目标的 SB 值，然后通过严格的 `fromParcel` 恢复对象。例如 i32 字段的 JSON `3` 直接读成 i32；不能先读为 i64 再转换。String 目标接收 JSON 字符串，char 目标检查恰为一个 Unicode 标量；这属于 JSON 文本解析，不是允许 Parcel 中的 String 转 char。
- 顶层容器目标（`Array`/`List`/`Map`，含可空元素/值与嵌套容器）的元素或键值声明为自定义对象/枚举时，走与对象目标相同的严格恢复入口：读取面构造与 SB 值 envelope 同构的 wire（目标类型名 + 受控 `..value` 载荷；每个载荷元素为记录形态——对象/枚举业务记录、标量 SB 值 envelope、嵌套容器子 envelope、声明可空的 null 为 wire null 哨兵），由已知静态 `T` 的严格 `fromParcel\<T>` 承担最终恢复。该 wire 形态是格式侧与合成恢复体的内部接口，不属于 JSON 表示契约；普通 JSON 的外观仍是 `[{...}]` / `{"k":{...}}`。
- 非可空目标遇到 null 报错。字段缺失及字段匹配遵循 §4.6.3，字段初始值不提供宽松 JSON 默认值。

#### 4.7.2 类型信息与引用

- 两参数 `write(value, output)` 默认保留类型信息。JsonSerializer 另提供 `write(value: Any?, output: OutputStream, keepTypeInfo: bool)`；`true` 使用本节的 Rigi 类型表示，`false` 使用 §4.7.4 的互操作表示。此选项属于 JSON，不加到 Serializer 的抽象方法上。
- 保留类型信息时，Rigi 对象附加 String 成员 `.rigi.type-identifier`。值为所表示实际类型的完整规范类型名，与 Parcel.typeName 一致，包含完整的闭合泛型实参；例如 `core.collections::Map<.string, .i32>`。从类型元信息取得标识，不调用业务对象可重写的 `toString()`；首版没有类型别名或版本迁移规则。
- 嵌套对象也输出实际类型标识，不因字段已经声明类型而省略。多态字段恢复实际派生类型，要求其已登记、可序列化且与目标声明兼容；不兼容的类型标识报错，不能强制转换为目标对象。
- 对象 Parcel 的合法业务字段与类型元数据分离。Serializable 枚举增加 String 成员 `.rigi.enum-case`，值为 case 名，实例字段按普通字段规则输出；不依赖编译器内部的枚举整数编号。旧的 `..case` 不出现在 JSON 中。
- 保留对象类型不要求每个标量或数组附带类型包装。直接输出的 `3`、`[]` 不保证恢复原始数值宽度或 Array/List 区别；动态值缺少足够类型信息时也不承诺这些区别的无损往返。
- JSON 不支持环形引用，不接受 `loopedRefEnabled`，包括继承的入口。对象便利入口使用树模式；遍历发现当前路径上的真环立即失败，已有显式图模式 Parcel 即使无环也拒绝，不能静默删去图信息。
- 无环重复引用按每条路径展开为独立副本，不保留别名。恢复结果不共享输入的可变内容；消息和深复制 API 的显式图模式不受此 JSON 限制影响。
- 写入失败可能已经输出部分字节，不回滚，不承诺事务性输出；检测环不要求先完整预扫描再写出。

#### 4.7.3 保留类型信息时的 Map 表示

- 所有 Map 均使用外层 JSON 对象：`.rigi.type-identifier` 声明完整 Map 类型，`content` 统一为键值对数组。String 键与非 String 键使用同一形式，空 Map 的 `content` 为 `[]`。这一不变量也适用于对象字段、Array/List 元素、嵌套 Map 以及经 `toParcel` 得到的集合载荷 envelope；内部交替键值 wire 只用于严格恢复，绝不能作为 JSON 数组泄漏。格式层须依据可靠的字段/元素声明或实际 Map 类型解释内部载荷，不得仅凭数组长度为偶数推断 Map；缺乏可靠类型依据时不得猜测键值语义。
- 条目按 Map 插入顺序排列，每项恰好具有 `key`、`value` 两个成员；条目是格式结构，不另加 Rigi 类型标识。`content` 不是数组、条目不是对象、成员缺失或多余均报错。
- 键和值使用正常的值映射及目标类型规则；不调用键的 `toString()`。String 键作为值保存，`.rigi.type-identifier`、`content`、`a.b` 和空字符串均可原样用作业务键。
- `content` 只在 Map 外层表示中承担载荷角色，普通对象仍可拥有名为 `content` 的字段。

以下是 `Map\<String, i32>` 的固定表示示例，类型标识不是占位文本：

```json
{
  ".rigi.type-identifier": "core.collections::Map<.string, .i32>",
  "content": [
    { "key": ".rigi.type-identifier", "value": 1 },
    { "key": "content", "value": 42 },
    { "key": "a.b", "value": 3 },
    { "key": "", "value": 0 }
  ]
}
```

数值或对象键同样放在条目的 `key` 位置。恢复时先按目标键类型恢复键，再按 Map 既有 `==` 语义判重；出现重复键必须报错，不能经 `Map.set` 静默覆盖。此规则独立于 JSON 成员名判重，不改变普通 Map 的更新语义。

#### 4.7.4 不保留类型信息的互操作输出

`keepTypeInfo=false` 递归作用于整个输出，去掉类型标识及 Rigi 特有表示约定，而不只是删去根对象的一个成员：

- 普通对象输出业务字段，不含 `.rigi.type-identifier`；标量与 Array/List 使用普通 JSON 值和数组。
- String 键 Map 输出普通 JSON 对象，键直接作为 JSON 成员名，值递归应用同一选项；不输出 Map 外层的类型标识或 `content` 包装。
- 该模式仅支持 String 键 Map。非 String 键 Map 报错，不把键转成字符串，也不回退到键值对数组；此边界同样适用于空 Map 和嵌套 Map。已知非 String 键的目标 Map 也不能从普通 JSON 对象的字符串成员名恢复，不能借 `readAs` 做键类型转换。
- 业务键本身名为 `.rigi.type-identifier` 时仍原样保留，包括其值为普通字符串的情形。该键不是生成的类型元数据，不能因关闭类型信息而丢失用户数据；普通 JSON 的 `readAs` 依据目标 Map 声明解释它，而不是仅凭键名或字符串值存在与否剥离。
- 无载荷枚举输出 case 名字符串；带载荷枚举输出普通对象，String 成员 `case` 承载 case 名，其余成员为各载荷字段，不输出 `.rigi.enum-case` 或类型标识。是否有载荷按应序列化的实例字段判断，不按 case 是否接受调用参数判断；固定 case 也可能有载荷字段。
- `readAs` 在已知枚举目标下按上述形式恢复：校验 case 存在，按反射中的字段声明读取载荷；格式成员 `case` 转为枚举元数据后，再进行严格业务字段匹配。缺失/未知 case、错误的形状或载荷字段不匹配均报错。如果枚举自身有名为 `case` 的载荷字段，本互操作形式会发生成员名冲突，读写均报错，不覆盖或改名。
- 不保证从该输出自动推回原始类型、派生类型或引用身份。目标类型已知时由 `readAs` 提供解释依据；若目标是抽象类型且没有足够的实际类型信息，则报错，不猜选一个实现。

上例关闭类型信息后的输出为：

```json
{
  ".rigi.type-identifier": 1,
  "content": 42,
  "a.b": 3,
  "": 0
}
```

此例中的四个成员全部是业务键。要按 `Map\<String, i32>` 恢复，应使用已知目标类型的普通 JSON 读取入口，不把业务键重新解释成 Rigi 元数据。

带 `errorCode: i32` 载荷的 `RequestResult.Failed`，保留类型信息时为：

```json
{
  ".rigi.type-identifier": "RequestResult",
  ".rigi.enum-case": "Failed",
  "errorCode": 404
}
```

关闭类型信息时为：

```json
{ "case": "Failed", "errorCode": 404 }
```

无载荷枚举的同名 case 则输出 `"Failed"`。这些形式由目标枚举声明解释，不把普通对象的 `case` 业务字段普遍当作枚举标记。

#### 4.7.5 数字、字符和容器

- 无目标类型时，整数词法先尝试 i64；超出 i64 但非负且可由 u64 表示时使用 u64；再超出即报错。带小数点或指数的词法使用 double，不把所有整数先经过浮点。
- 有整数目标时，只接受整数词法并检查符号与范围；`3.0`、`3e0` 不作为整数输入，禁止截断或溢出回绕。有 float/double 目标时，直接按该精度解析数值词法并舍入；超出有限范围报错。源码类型名为 `float` / `double`，分别对应 f32/f64。
- 输出浮点采用能恢复原浮点值的最短表示，保留浮点负零；NaN、正负无穷均报错，不替换成 null 或字符串。无目标读取不承诺保留输出前的浮点宽度。
- char 按 §4.3.1 的 32 位标量语义输出为含一个 Unicode 标量的 JSON 字符串；String 输出为普通 JSON 字符串。读取 char 目标必须检查标量数量和合法范围，支持补充平面标量，不把 UTF-8 字节数或 UTF-16 码元数当作字符数。
- Array/List 输出为数组。类型引导读取时严格按元素声明构造对应集合；无目标读取统一得到 `Array\<Any?>`，空数组不提供额外类型线索。
- bool 只对应 JSON 布尔值，null 只对应空值；不存在 String/bool 到数值的宽松解析或以空串代替 null 的规则。

#### 4.7.6 文本格式、编码、限制与错误

- 严格读取一个完整文档：根值之后只允许 JSON 空白直到 EOF；拒绝空文档、第二个根值、注释和尾随逗号。首版不提供拼接多文档的连续读取协议。
- 拒绝所有 JSON 对象中的重复成员名，包括元数据成员；在字符串转义还原后比较名字，因此 `"a"` 与 `"\u0061"` 重复。这是本库策略，不宣称 RFC 要求所有解析器拒绝重复名。
- 默认输出紧凑格式，可配置基础缩进，不附加末尾换行。生成的元数据在前，业务字段按 Parcel 迭代顺序，Map 按插入顺序；输入中的类型元数据可位于任意位置，解析不能依赖输出顺序。
- 字节输入/输出默认 UTF-8。JsonSerializer 提供专用编码配置 API，复用 `core.text` 编解码能力；Serializer 基类不声明该 API，也不跟随系统代码页。编码配置用于一次调用的完整文档，不在处理中途切换。
- UTF-8 输入允许开头的一个 BOM，输出不生成 BOM；不按 BOM 自动猜测其他编码。显式选择其他编码时按该编码严格解码，不能静默退回 UTF-8。非法编码、非法转义及未配对代理值报错，不用替换字符掩盖损坏。
- JSON 容器嵌套深度默认上限 256，并允许配置更小上限；根对象/数组深度为 1，标量根为 0。另外可配置总输入字节数、字符串和数字 token 大小限制；未指定大小上限仍受实际容器容量约束。既有对象编解码的深度限制继续生效，不因 JSON 限制而取消。
- 语法、表示、数值范围及 JSON 资源限制错误使用 `JsonException`，提供原因和从本次输入起点计的零基字节偏移；偏移按实际输入编码计，包括已消费的 BOM，不按转成 UTF-8 后的位置计。写出错误没有虚构的输入偏移。
- 对象恢复异常及底层 I/O 异常原样传播，不伪装成 JSON 语法错误，不聚合异常；清理遵循既有单异常展开语义。
- 配置由 JsonSerializer 的构造选项承载，包括编码、缩进和限制。每次调用有独立解析状态，同一实例可顺序复用，但不支持并发或重入调用。所有入口借用流、不关闭且不隐式 flush，遵循 §4.6.2。

JSON 的类型信息和互操作形式均不构成另一套私有二进制格式。对未承诺保留的类型区别，不宣称无损往返。
